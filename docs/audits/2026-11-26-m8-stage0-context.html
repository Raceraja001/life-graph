Summary

  • Most building blocks already exist. Bitemporal helpers (is_valid_at, recorded_time_of, is_bitemporally_valid), an as_of/recorded_as_of retrieval path, non-destructive supersession with undo, evidence/trust labels, entity linking, decisions with supersession, intentions, a local-only relevance judge, and a non-executing proposal path into the approval queue.
  • There is no assembler. Jarvis context is stitched inline in ProcessManager._run_agent and flattened to text; memory ids survive only in the turn trace. Decisions, intentions, projects and tasks never reach Jarvis chat context. The daily brief is the closest thing to a multi-source state view.
  • Production data is thin for M8. On every active memory valid_from equals created_at (world time is not actually captured); valid_until is never set; 1 superseded row; 11 decisions, all candidate; 0 predictions; 1 intention; 0 connector items; 180 links, all ASSOCIATED; AGE graph has 24 vertices. A context layer built now will mostly surface memories, and should say so rather than imply richer state.
  • No goal / commitment / constraint record exists anywhere. Per the Charter (no domain enums in the core) these must stay flexible labels on derived items, marked inferred unless a user-stated source exists.
  • Stage 1 needs no migration. A snapshot is a computed, ephemeral read model; the existing turn trace (agent_tasks.result JSONB) can hold its references. Stage 2 (comparison) and Stage 3 (usefulness feedback) probably do need persistence — that decision is deferred to an ADR at that stage.
  • Pre-existing security/privacy findings (independent of M8, but M8 must not build on them): service API keys are not bound to a tenant; raw Cypher “admin” is a header check; several cloud-egress paths exist in code defaults (closed in prod by configuration today); watchers ignore the kill switch; audit_log is empty for every tenant. See §6–§7.

5. Missing capabilities and gaps

  1. No single assembler / structured snapshot. Context is flattened text; no item list with source refs, inclusion reason, exclusions or an explicit “insufficient context” result. missing
  2. World time is not captured in practice. 0 active memories have valid_from ≠ created_at; valid_until never set. Supersession is the only working temporal signal. The assembler must label validity as “since recorded” rather than claim world time. O
  3. valid_from and superseded_at are filtered in Python only (retrieve() :743); /search never checks valid_from; superseded_at lives in JSONB, not a column. Fine for a read model; note for performance.
  4. No goal / constraint / milestone records. Must be derived, flexibly labelled, and marked inferred.
  5. Projects are not linked to memories or entities (no column; agent_tasks.project_id has no FK). Project context can only be matched by entity key/name — heuristic, must be labelled.
  6. No memory-change events. MEMORY_UPDATED/DELETED/RETRIEVED defined but never emitted; no memory:superseded, no entity.*; MEMORY_CREATED only for shared-context (events.py:39-148, shared_context.py:145). Event payloads need not carry tenant_id. → a cache or change detector cannot subscribe today. Stage 1 therefore uses no cache.
  7. Redis bridge is publish-only; nothing re-emits across processes (events.py:323-366). Likely bug: WS subscriber splits events:{tenant}:{type} as split(":",1)[1] → "tenant:type", so bridge events never reach a socket (websocket.py:169, verified by reading; not run).
  8. No feedback store for briefs/recall/findings (MemorySession.was_useful has no writer). Stage 3 needs one.
  9. Hard delete: DELETE /memories/{id} is a hard delete (postgres.py:416-436); the MCP forget docstring claims soft delete (mcp_server.py:370-377). Conflicts with “correction without destroying provenance”.
  10. Retrieved memory not fenced as untrusted in Jarvis’s memory block (only “unverified” label), while drivers/context.py:45-52 does fence. Tool and child results return raw (orchestrator.py:427-433).
  11. Determinism: retrieve() ends with an LLM judge (retrieval.py:62). A reproducible snapshot needs a judge-off path.
  12. No two-tenant search isolation test. test_progressive_disclosure.py:236 only greps source for “tenant”.

  • Applied at the storage layer: storage/postgres.py reads get_current_tenant_id() on every memory query (e.g. :339, :462, :521/558, :764); graph walks scope every vertex (graph.py:152-169); entities filter both tables (entities.py:234,414-441). IT
  • No Postgres RLS on any table/schema (verified in prod catalog). O
  • High — API keys are not tenant-bound. verify_service_key only checks list membership (api/auth.py:106-154); any key holder picks any X-Tenant-ID. Raw Cypher /graph/query is “admin” only when the tenant header equals default (api/graph.py:226-231), and the graph falls back to default with no context (graph.py:40,102-106). Single-owner deployment limits the blast radius today, but it is a real boundary gap. Not an M8 change — reported for a separate decision.
  • Low-Med — create_link does not check that both memories belong to the tenant (services/memory/links.py:85-108).
  • Personas: a delegated child inherits the tenant; spawn only re-checks the persona exists for that tenant (process_manager.py:157).   • Lore tables (lore_nodes/lore_edges) have no tenant_id; they hold public Tamil-knowledge data, not personal records — out of M8 scope; the assembler must not read them.

8. Proposed smallest slice (Stage 1)

Consumer: a Jarvis personal turn, in shadow mode. Jarvis is the only consumer that already has a local-only route, a provenance trace and a correction button (“memory was wrong”). A project-task consumer would need project↔memory linkage that does not exist.

What it does: a read-only, deterministic assemble_context(tenant, query, purpose, as_of, budget) that returns a typed snapshot:

  • items — each with source_ref (kind + id: memory / decision / intention), dimension (free-string label from tags or source kind, never an enum), origin (user-stated / imported / extracted / model-proposed, mapped from source_type, trust_tier, extraction_tier, status pending), evidence label, valid_from/recorded_at with a flag when world time is unknown, freshness class, reason included (vector hit, keyword hit, entity link, neighbour, open intention, decision).
  • conflicts — pending contradiction pairs and superseded-by chains shown side by side, never merged.
  • exclusions — counts and reasons (expired, superseded, pending-only, over budget).
  • insufficient — explicit flag when nothing passes the evidence bar.
  • deterministic ordering (score, then recorded time, then id) and a hard character/item budget.

Sources in Stage 1: memories (via existing hybrid_search + bitemporal helpers + entities.memories_for, judge off), decisions (candidate labelled “proposed, not decided”), pending intentions. No projects, tasks, connectors yet.

Wiring: behind a new flag LIFE_GRAPH_CONTEXT_SNAPSHOT_SHADOW (default off). When on, a personal local Jarvis turn also builds the snapshot and stores its compact form (refs, labels, reasons — no content) in the existing turn trace. The prompt is unchanged in Stage 1. A read-only GET /api/v1/context/snapshot?q=… returns the snapshot for inspection and eval.

Not in Stage 1: prompt changes, caching, change detection, feedback, proactive output, new tables, any model call beyond the local query embedding.

Prerequisite PRs (small, test-first, no behaviour change)

  1. Two-tenant isolation integration test for hybrid_search, retrieve(), entities.memories_for and /search (seeds tenants A and B, asserts zero cross-reads).
  2. Judge-off switch on retrieve() (parameter, default unchanged) so a snapshot is reproducible.

10. API compatibility and performance

  • Compatibility: purely additive — one new GET, one optional trace field, one default-off flag. No existing response shape changes; phone and web clients unaffected.
  • Performance: current prod /search ≈ 1.4 s, most of it embedding + local judge. Snapshot (judge off) = 1 local embedding + 1 hybrid_search + 2 indexed lookups (decisions, intentions) + entity lookup. Budget: p50 ≤ 400 ms, p95 ≤ 1 s on the prod tenant, measured by the eval script; shadow mode runs it concurrently with the existing memory block so turn latency should not grow (to be measured, not assumed). Snapshot size cap: 40 items / 6 000 chars.

11. Is persistence or a migration needed?

  • Stage 1: no. The snapshot is computed on demand from existing rows; its reference list fits in agent_tasks.result JSONB, which already stores the trace. No cache is added (and no invalidation events exist to support one safely — §5.6).
  • Stage 2 (comparison): probably. Comparing “since last interaction” needs the previous snapshot’s refs; the turn trace can serve for Jarvis, but cross-consumer comparison would need a small table. Decide by ADR then.
  • Stage 3 (feedback): likely yes. No existing table records useful/not-useful/already-handled for derived items; corrections covers only “incorrect”. ADR + migration + retention rules at that stage.
