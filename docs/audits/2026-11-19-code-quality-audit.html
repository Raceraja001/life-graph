Life Graph code quality audit

Read-only, evidence-based baseline · master 3380d81 · 19 Nov 2026 · no code was changed

1. Executive summary

Life Graph is a large codebase: 142k lines of application code and 110k lines of tests. The basics are clean. Ruff and formatting pass, master CI is green, and integration tests run against a real Postgres with pgvector and AGE. Deprecated Pydantic, SQLAlchemy and asyncio patterns are almost entirely gone. 84% of public service functions have docstrings. The dev-agent container runtime was hardened and reviewed this week.

The weaknesses fall into five themes:

  • Trust boundaries are weaker than the design says.
    • Approvals are meant to be "the person decides", but any service key can approve, and the request body names who decided.
    • A project's backup_check_command runs as a shell command on the host, set through an ordinary API key, with no approval step.
    • The redaction used for Claude Code transcripts and Telegram misses current API-key shapes (5 of 5 tested leaked).
  • Side effects are not idempotent.
    • Approving the same item twice at once can deploy twice: there is no row lock, and a timed-out deploy is never killed.
    • Capture deduplication overwrites the original event's status, and Telegram replays can create duplicate memories.
  • Database transactions are held open across slow calls. Capture holds a transaction open during the language-model extraction step. Postgres has no idle or statement timeout to reclaim it, and the connection budget is about 45 per process.
  • Tests pass when the code fails.
    • 266 integration-test assertions accept HTTP 500.
    • There is no coverage measurement.
    • About 7.7k lines of services and API code are never imported by any test.
    • Migration downgrades and model/schema drift are never tested.
  • Builds aren't reproducible. uv.lock is stale and unused, every dependency is an open >= range, and CI has no vulnerability scan.
Context for severity. No finding is exploitable without a valid API key, apart from metrics flooding, which needs none. Prod binds to 127.0.0.1, and the key holders are your own tools: Claude Code hooks, the MCP server, the phone and the dashboard. That is why nothing is rated Critical. The High items matter because they turn "a tool holding a key" into "runs host shell, approves its own merge, or deploys twice". That breaks the autonomy design's guarantees, and the impact grows as soon as more keys or users exist.

3. Architecture overview

Request path. main.py builds the FastAPI app. Each request passes through RequestID, Auth (global; exempt paths are in api/auth.py:22-38), Tenant, RateLimit and Logging. The app mounts 55 router modules with 399 routes. Routers get singletons from runtime.py: 52 cached get_* providers, a documented service-locator choice. Many routers open their own DB sessions and commit inside the handler. That puts business logic in the API layer: api/assistant.py has 40 session opens, and api/kernel.py has a 203-line chat-stream route.

Layers below the API:

  • services/: domain logic, six packages plus about 92 flat modules and 57 alias shims.
  • core/: memory manager, tenant, evidence, trust and the event bus.
  • storage/: postgres.py, hybrid.py and graph.py for AGE.
  • The agent stack: agents/orchestrator, then kernel/process_manager, then drivers/, then services/dev/*, which uses the container task runtime.
  • autonomy/: a separate approval queue and pipeline.
  • watchers/: a separate notification engine.

Background work runs as 35 arq cron jobs in workers/ plus the dedicated dev-task runner.

Boundary health. The layers are mostly respected, with leaks in both directions:

  • storage imports api twice, and services imports api twice. Both directions are wrong.
  • core imports services 9 times.
  • 41% of files rely on imports inside functions to work around import cycles.
  • There are two overlapping subsystems:
    • Approvals: the main approvals list in services/approvals.py and the separate autonomy approval queue in autonomy/approvals/, which copies its items into that list.
    • Notifications: kernel notification records and watcher deliveries, kept in two separate tables.

H1 · Secret redaction misses modern API-key shapes potential security · S · quick win
Where
life_graph/core/redaction.py:33-39, used by integrations/claude_code/transport.py:97,106 (all Claude Code capture content) and integrations/telegram/router.py:314,378
Evidence
The pattern \bsk-[A-Za-z0-9]{16,}\b stops at the first hyphen. I ran redact_secrets() on sk-ant-api03-…, sk-proj-…, sk-or-v1-…, AIza… and github_pat_…: all five leaked. A separate module, services/redaction.py:16-27, already covers them, and a third pattern list sits at services/dev/verifiers.py:795-806. Capture ingest has no server-side redaction.
Why it matters
Claude Code transcripts are exactly where Anthropic and OpenRouter keys appear. They become stored captures and memories, and they can be echoed to Telegram.
Fix
  1. Make one canonical pattern set, the union of the three lists.
  2. Have core.redaction delegate to it.
  3. Also redact server-side in services/capture.py.
  4. Consider a one-off scan of existing captures for these key shapes. This is an owner decision.
Change risk
Low. It only adds patterns; at worst, some prose starting with sk- gets redacted.
Regression test
A parametrised test running every key shape through all three redaction functions and through the capture transport, asserting the raw secret never survives.
H2 · Any service key can make the host run shell commands, with no approval potential security · M · long-term
Where
api/kernel.py:1423-1431 (deploy_command, smoke_command, rollback_command and backup_check_command are free strings), the register and update routes at :1565-1597 and :1673-1692, watchers/app_uptime_watcher.py:152-153,215-223, and services/approvals.py:1115-1120 (create_subprocess_shell)
Evidence
The hourly run_watchers job calls _run_shell(meta["backup_check_command"], project["path"], …) for every tenant. No approval or owner check sits anywhere on that path. Deploy commands do at least run behind an approval.
Why it matters
Holding any key amounts to a shell on the home server as the worker user. That includes keys held by agents and tools.
Fix
Require an owner-verified caller (ingress_for(request).owner_verified) to set any *_command field. Better still, file an approval when a command changes, and run only commands whose hash was approved.
Change risk
Medium. The dashboard and phone flows that edit projects need the owner key.
Regression test
A PATCH of backup_check_command with a non-owner key returns 403. The watcher refuses a command whose hash was not approved.
H3 · The human approval gate is not tied to the owner's identity architectural / potential security · S · quick win
Where
api/approvals.py:44-56 (resolved_by = body.resolved_by unless the caller is a paired phone) and :95-105. ingress_for() is used only at api/memories.py:91,423.
Evidence
The approve and reject routes accept any service key. The MCP server deliberately leaves out approve (mcp_server.py:60-65), but a client holding the same key can POST /approvals/{id}/approve directly.
Why it matters
An agent can approve its own merge, deploy or plan. The audit field resolved_by is written by the caller, so the record can't be trusted either. Your rule that approvals belong to the owner is only enforced by convention.
Fix
Require owner_verified (an owner key or a paired device) on approve and reject. Derive resolved_by from the caller's identity, not the request body.
Change risk
Low to medium. Any client that approves needs the owner key.
Regression test
A non-owner key gets 403 on approve, and a resolved_by value in the body is ignored.
H4 · Two approvals of the same item at once both run its side effect; timed-out deploys keep running confirmed defect · M
Where
services/approvals.py:187-191 (session.get, then a status check with no with_for_update; no row locking anywhere in the file), :469-546 (deploy, then smoke test, then rollback, all inside the request), :495-503 and :1120-1129 (on timeout the code raises or returns 124 but never kills the process), and retry_auto_merges at :1134-1170
Evidence
The commit happens only at api/approvals.py:80, after side effects that can last up to 600 seconds. Until then a second request still sees the item as pending. The cron job that retries auto-merges also reads the same pending rows without a lock.
Why it matters
A client timeout followed by a retry, or approving from the phone and the dashboard, gives two concurrent deploys or merges. A timed-out deploy is left running while its retry starts.
Fix
  1. Claim the row atomically first: UPDATE … SET status='applying' WHERE id=:id AND status='pending' RETURNING ….
  2. Then run the side effect.
  3. On timeout, start the command with start_new_session=True and kill its whole process group with killpg.
  4. Longer term, run deploys as worker jobs.
Change risk
Medium. It adds an applying status that the UI must handle.
Regression test
Two resolve() calls run concurrently on one deploy approval give one shell call and one 409. _run_shell("sleep 30 & sleep 30", …, 1) leaves no child process behind.

H6 · Builds are not reproducible: a stale, unused lock, open-ended ranges and no vulnerability scan potential security · M · quick win
Where
pyproject.toml (42 of 44 dependencies are >= ranges), uv.lock (last committed 3 Oct; missing pytest-xdist and playwright), .github/workflows/ci.yml:75,130,280 (pip install -e), Dockerfile:19-25, and the CI cache key ci.yml:58-62 (keyed on pyproject.toml; a cache hit installs with --no-deps)
Evidence
Nothing runs uv sync, uv export or --frozen. pip-audit is installed but only used by the dev agent's own check; CI has no audit job, and there is no dependabot or renovate config. The ranges allow major-version jumps, for example fastmcp>=2.0 resolving to 3.x, and litellm, which has had a supply-chain incident.
Why it matters
A compromised or breaking release flows straight into prod. CI may test frozen old versions while a fresh build pulls new ones.
Fix
  1. Run uv lock.
  2. Install from the lock in CI and Docker (uv sync --frozen, or uv export then pip install --require-hashes).
  3. Add uv lock --check to CI.
  4. Add a pip-audit job and dependabot.
  5. Key the CI cache on uv.lock.
  6. Cap major versions of fast-moving libraries.
Change risk
Low to medium. The first lock may change resolved versions, so run the full suite.
Regression test
The uv lock --check CI step.
H7 · Capture holds a DB transaction open during the language-model call, with no server-side timeouts confirmed defect (reliability/performance) · S-M · quick win
Where
services/capture_processors.py:138-146 (a SELECT starts a transaction), :202 (await …extract(content, capture=True), LLM-first), first commit at :226. Engine settings: storage/database.py:7-14.
Evidence
The author fixed the same problem for the later wait (comment at :225), but not for extraction. The same pattern appears in:
  • api/sessions.py:196-216: an LLM summary inside the request transaction, with a racy ended_at check.
  • workers/embeddings.py:79-113: one embedding call per memory inside a session, although embed_batch_async exists.
  • services/transcript_distiller.py:73-132.
No statement_timeout, idle_in_transaction_session_timeout or command_timeout is set anywhere.
Why it matters
Each process can open about 45 connections: SQLAlchemy 10+20, the graph pool 10 and the approvals pool 5. Prod and dev share one Postgres. A burst of captures can use them all up, and nothing reclaims connections left idle inside a transaction.
Fix
  • Read the data, commit or close the session, make the LLM call, then reopen the session to write.
  • Set server_settings on the engine with idle_in_transaction_session_timeout of 60 s and a statement timeout. Long jobs can opt out with SET LOCAL.
  • Batch the embeddings.
  • Document a connection budget.
Change risk
Low for the session split. Medium for timeouts, because long consolidation or backfill jobs need an explicit exemption.
Regression test
Mock extract to sleep and assert session.in_transaction() is false meanwhile. Add a config test for server_settings.
H8 · The session-end job closes the shared graph pool; its duplicate check is dead and its links are lost confirmed defect · S · quick win
Where
services/memory/micro_consolidation.py:204 (calls search_by_embedding, a method that exists nowhere in the repo), :331-363 (vertices get inferred labels, but edges match only Entity), :367-368 (graph.close()), storage/graph.py:327-329 (close() calls the process-wide close_pool())
Evidence
The job runs after every POST /sessions/{id}/end. Three faults:
  • The missing method raises AttributeError, which is swallowed at debug level, so duplicates_removed is always 0.
  • Edges to Person, Project or Technology vertices never match, yet edges_created is still counted.
  • Where edges do match, CREATE makes a duplicate edge on each run.
Why it matters
Graph queries running at the same moment fail when the pool closes, and the next call rebuilds it. A memory feature is silently doing nothing.
Fix
  • Remove the close call; keep close_pool() for shutdown only.
  • Call the real search_similar.
  • Pass the inferred labels to the edge match.
  • Use match-or-create for edges.
  • Count only edges actually created.
Change risk
Low for the pool fix. Medium for dedup, because it starts superseding memories; use a conservative threshold and keep it within one tenant.
Regression test
The pool is still open after _update_graph. Two near-identical embeddings give duplicates_removed == 1. A fake graph store receives the inferred labels.
H9 · The two approval stores drift apart; an owner's reject can be silently ignored confirmed defect · M · quick win
Where
services/autonomous_approvals.py:236-278 (copies each autonomy-queue item into the main approvals list as kind="autonomous_action"), autonomy/approvals/service.py:258-300 (check_expirations), autonomy/approvals/router.py:58,85, services/approvals.py:1013-1093
Evidence
autonomy/approvals/service.py never touches the copied row in the main list. When an autonomy item auto-approves on expiry, its copy stays pending. If the owner later taps Reject on that copy, the "already resolved" error is treated as a harmless repeat tap and logged at info level. The copy then shows rejected while the action was actually approved.
Why it matters
The owner sees one decision and the system acts on the other.
Fix
Close the copied row in the same transaction on every autonomy-queue resolution: resolve, batch and expiry. Alternatively, make the main list a view over the queue. When the two decisions differ, return a conflict instead of reporting success.
Change risk
Medium. This is the human-in-the-loop path.
Regression test
Expire an item that is set to be told to the owner first, and assert its copy is resolved. A reject after an auto-approve returns a conflict.

6. Rules for doing the fixes without destabilising prod

  • One finding per PR. Write the regression test first and see it fail on master.
  • For anything touching approvals, capture or the dev-agent loop, run the reliability eval and the agent benchmark before merging.
  • Two changes alter behaviour you rely on, so release them one at a time with a quick live check: owner-only approvals (H3), and statement timeouts (H7).
  • Deleting code (L1 aliases, L2 dead schemas) and any one-off scan of past captures (H1) wait for your explicit OK.
  • Re-measure the baseline in section 2 after each batch.

7. What was checked and found sound

These are listed so they don't get re-flagged:

  • The f-string SQL in storage/postgres.py:474,512 only splices constants.
  • Cypher value escaping is sound.
  • All 61 migrations are on one linear chain, and every new NOT NULL column has a default.
  • The global exception handler doesn't leak internals.
  • Every except BaseException re-raises, and CancelledError is handled correctly.
  • No pickle, yaml.load or eval in app code.
  • Uploaded filenames are sanitised.
  • WebSocket auth is correct, and device tokens are limited to an allowlist.
  • Effectively every outbound httpx call has a timeout.
  • arq cron jobs can't run twice at once.
  • Database transactions used for locking commit straight away (the dev runner's advisory lock).
  • Integration tests use an isolated, truncated test DB.
  • LLM calls go through one resilient client.
